## Payment isolation

Without credentials, the **explicitly labeled local simulator** provides success,
decline and cancellation. It collects no card numbers, sends no payment request,
places no order and sends no email. This is not a verified Stripe transaction.

An implemented Stripe adapter accepts only the dedicated
`FIREWOOD_STRIPE_TEST_SECRET_KEY` environment variable. It rejects live and
publishable keys and never falls back to CRM's `STRIPE_SECRET_KEY`. Before using
the adapter, provision a key from a confirmed isolated Stripe sandbox without
CRM webhooks, customer notifications or live customer data. Do not paste keys
into chat or commit them. The October 24 sandbox run uses a mode-600,
Git-ignored `.env.firewood-sandbox.local` file. Start it with
`node --env-file=.env.firewood-sandbox.local scripts/firewood-checkout/server.mjs`.

The Stripe plugin confirmed Angel Tree Services' live account but did not expose
general-sandbox creation. A dedicated local CLI profile created an isolated,
unclaimed Stripe sandbox, `acct_1UU9U8RAZXGe6tX0`, expiring October 31, 2026.
It is not yet claimed under Angel's account. Greenpro's browser login, Angel's
live settings and CRM settings were not changed. Initial sandbox checks found
zero webhook endpoints, event destinations and Checkout Sessions. The claimable
sandbox's restricted key format is `rkcs_test_`; live equivalents are refused.
Do not use this temporary environment as a production account or silently
claim it through Greenpro's browser session.

With that key supplied to the local process, the adapter creates a hosted Stripe
test Checkout Session using server-calculated prices and a fixed loopback return
URL. It checks `livemode === false`, a test-session ID, the official Stripe
checkout destination and server-side paid status, reference, currency and amount.
The return URL alone never proves payment. A local signed webhook handler also
checks paid status against Stripe before clearing the bound order. It accepts
only test `checkout.session.completed` and
`checkout.session.async_payment_succeeded` events, ignores unrelated/unpaid
events and tolerates duplicates. The official CLI forwards only those events
from this sandbox to the loopback handler; its signing secret is held in
`FIREWOOD_STRIPE_TEST_WEBHOOK_SECRET`. No public webhook was deployed. No receipt
email or invoice creation is requested. No tax calculation or Stripe promotion
is configured. The current adapter sends the revised, undiscounted checkout
line items; earlier veterans-discount provider tests are historical evidence.

Identical submissions share one Checkout Session. Retrying an expired Stripe
session now creates a fresh attempt; paid sessions cannot be charged again,
and completed-but-unpaid sessions return a processing message. Provider failures
preserve the local order. The test uses Stripe's dynamic payment methods; only
cards were exercised end to end. Wallets, bank payments and buy-now-pay-later
methods remain unverified and need an explicit payment-method policy before
live release.

The loopback server limits request size, requires same-origin JSON and a session
CSRF token, refuses foreign Host headers, uses no-store/noindex responses and
blocks external connections from the local pages with a restrictive CSP.
The checkout loads no analytics, consent, estimate or CRM scripts.
No card details pass through Angel's server or form.

## Durable test orders and confirmations — October 25

The preview now uses a disk-backed Postgres-compatible database from
`@netlify/database-dev` 1.0.1. Its private, Git-ignored `.firewood-test-data/`
directory has mode 700. It survives graceful restarts and abrupt process
termination; it is **local test storage**, not a hosted production database or a
backup. A single-process lock prevents simultaneous writers to the embedded
engine and recovers stale locks when the recorded process no longer exists.
The local database listens only on loopback. No cloud resources were provisioned.
No existing Netlify/CRM database or connection string is read.

An immutable attempt stores its server-calculated quote and delivery/contact
snapshot **before** opening payment. A successful, verified test payment records
its paid state and queues exactly one customer confirmation and one owner
notification in the same transaction. Order references start `FW-TEST-`.
Payment references are restricted to Stripe test sessions or the local simulator.
All delivery charges remain zero; stacking is $150 once. Declines and unpaid
sessions do not queue confirmations. Signed paid events can find their saved
attempt after browser expiry, browser reset, selection changes or server restart.
Duplicates and asynchronous payment-success events share the same confirmation
records. A browser return can reconcile payment but is not required for capture.

Confirmation delivery is deliberately a **local capture sink**: no SMTP, email
provider, live recipient delivery, CRM task, reservation or dispatch occurs.
Customer and owner copies include amount, free delivery, optional stacking,
contact/address/instructions, the promise to provide a delivery date within a
week, and the 48-hour cancellation terms. Owner destination is fixed to
`info@angeltreeservice.org`. Messages are clearly marked TEST. Failed captures
remain pending and retry after 30 seconds, including after restart. Capture and
acknowledgement commit together; a replay cannot create duplicate captured copies.
Actual email delivery semantics and provider idempotency have not been tested.

A completed browser session can open **View test confirmation** for its own
customer copy. No public owner/order-list endpoint exists; guessing another order
reference does not grant access. The browser authorization cookie expires after
30 minutes and is HttpOnly, SameSite Strict (simulator) or Lax (Stripe return).
Contact fields leave the form after success, but persist in the private order
record; the test notice and result wording say this explicitly. Starting another
test clears browser authorization, not the saved order. In Stripe mode, synthetic
contact/shipping details also persist in Stripe's test environment. No browser
storage is used. No card data, raw event bodies, credentials, request logs or
provider diagnostics are stored as orders or confirmations.

For private owner inspection, stop the preview and run
`node scripts/firewood-checkout/orders.mjs` to list test order summaries, or append
an exact `FW-TEST-…` reference to view the saved details and both confirmations.
Output can contain personal information; use synthetic details only and do not
paste real customer records into reports. Restart `npm run preview:firewood`
afterward. The preview never falls back to an in-memory store if its configured
disk database fails to open, and it refuses to open payment if the order snapshot
cannot be saved.

The SQL migration lives under `scripts/firewood-checkout/migrations/`, outside
Netlify's automatic production migration path. The main public build has no
checkout/database dependency or endpoint. Moving these records to a separately
owned hosted database with backups, retention/access controls and a functioning
notification worker is a future release step, not performed by this patch.
