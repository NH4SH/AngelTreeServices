# Firewood native release runtime

The owner approved installation, final testing and launch on October 30, 2026. This directory is the separate native runtime implementation. Source preparation does not itself install or activate anything. Frozen `office-v2/`, `office/`, `live/`, `customer/` and historical evidence remain unchanged.

## Architecture

- `main.mjs` starts only `web` or `worker`, as an unprivileged process on the existing private service network. It loads root-owned readonly Website component metadata from `/release-admission/website-runtime.json`. The exact shared master control remains `/release-admission/firewood-release.json`; its schema and signed recovery-certificate format are not changed here.
- `integrity.mjs` verifies the component's `releaseControlSha256`, installed source manifest and fixed native-proof module before reading any mounted credential. Metadata/module manifests are root-owned readonly files; runtime source is root-owned and unwritable by the application user. Credentials are read only from fixed `/run/secrets/*` names, never environment flags, browser data or public assets.
- `database.mjs` binds a pg-compatible pool to the actual `postgres` database, `app_private` schema and exactly `ats_firewood_request` or `ats_firewood_worker`. Every transaction explicitly uses READ COMMITTED and fixed search_path. BEGIN and preCOMMIT recheck actual connection identity plus root's combined signed master/native proof. Binding compares actual system ID, source/schema release hashes, recovery-binding byte hash and authority SPKI fingerprint. Proof must have monotonic backup age under 280 seconds and a native lease expiring within 14 seconds. No UUID certificate or substitute authority is invented.
- `native-proof.mjs` is supplied by the CRM-owned root installer as a hash-pinned readonly module under `/release-admission/`. Its `createAdmissionVerifier({descriptor,role,mode,binding})` combines independently verified current signed backup/boot/generation/clock context with `app_private.fwofficev2_native_context()` and checks the master control twice. Website does not install the helper, create roles, mutate grants, or infer admission from table presence.
- New order/price acceptance transactions require fresh preparation+office modes; payment resumption requires collection+office; confirmation sends require sending+office. Request state rechecks effective master gates. Startup booleans cannot override a later pause. Status/reconciliation remain possible with new orders/sending disabled when the actual status authority permits them.
- `transport.mjs`, `live-client.mjs`, `office-client.mjs` use the exact five approved production operations, canonical request validation, distinct financial/office signing domains, the fixed CRM HTTPS origin, no redirects, bounded request/response bodies and timeouts. Master HMAC identity/fingerprint must match the mounted HMAC secrets. Website contains no Stripe key, payment webhook or second collector. No financial-only status fallback exists.
- `orders.mjs`, `policy.mjs`, `service.mjs` preserve the reviewed domain behavior in a distinct runtime adapter. Native installation is deliberately refused by the source/test installer: CRM owns guarded DDL/enrollment. Actual native clients cannot borrow a disposable database, and isolated clients cannot borrow actual native storage. Polling rotates fairly through prepared orders using `next_status_at`.
- `server.mjs` serves the preserved customer assets behind a fixed private gateway proof and exact checkout Host/Origin. Its session is a secure host-only `__Host-` cookie, HttpOnly and SameSiteStrict. It bounds request bodies/time, validates CSRF and actions, blocks fixture endpoints, and returns no-store/noindex/CSP. Only the root-managed gateway may publish the backend; PostgreSQL has no public listener.
- `worker.mjs` leases a bounded retry/status/outbox batch, records aggregate heartbeat/status without customer data, and resumes without duplicating accepted orders or messages. Native role/grant/health/capture/commit protections are owned by the CRM installer; the read-only health role uses its aggregate helper, not this worker's raw status queries.

## Confirmation authority

CRM remains the payment receipt authority. Website owns one customer order confirmation and one owner notice to `info@angeltreeservice.org`, sent from `orders@firewood.angeltreeservice.org`. These are distinct messages/purposes with stable separate idempotency keys. The owner approved both; their gates remain off during preparation.

`confirmations.mjs` captures exact original paid evidence, accepted amount/details and frozen message payloads only after a fresh paid-active-accounting observation. Capture rechecks the locked stored receipt to refuse an intervening cancellation. Credit never becomes payment/refund or fulfillment. Dispatch obtains fresh admission/lifecycle evidence again; cancellation/credit suppresses unsent notices. Parallel jobs use durable leases. A lost provider reply retries the same payload/key; after 23 hours uncertainty requires office review before provider idempotency retention can expire. Accepted/review/suppressed history, recipient, payload, identity and first send cannot be reset through the ordinary runtime.

`mailer.mjs` has a fixed Resend endpoint/sender, bounded replies and redacted errors. Controlled-test mode can deliver only to the approved owner inbox and uses a separate test identity. Live sending additionally requires component gates and the actual master sending mode. The mounted sender key fingerprint is checked before constructing it. No existing Stripe account receipt settings are changed.

## Storage and installation

Fifteen `fwofficev2_*` tables share the existing CRM physical WAL and paired recovery cutoff: identity, sessions, control, rate, drafts, price_queue, prices, price_history, orders, prepare, observations, history, confirmations, outbox and heartbeat. There is no dependency on PUBLIC business tables. Root installs/enrolls these alongside the ten CRM profile tables, with actual write/schema/commit/truncate guards, explicit grants and fresh recovery evidence. `schema.sql` is source-derived DDL only, with no role, source, credential, identity-hash, recovery or activation seed. Never execute it as an unguarded migration.

`export-schema.mjs` runs only in a newly owned disposable engine and captures the pinned office-v2 installer plus confirmation extension. It does not connect to actual storage. Actual installer readback and whole-source/DB fingerprints remain separate requirements.

## Verification and remaining interfaces

Local focused tests cover confirmation identity/lost replies/age/concurrency/cancellation, explicit native identity/mode/lease/commit fencing, secure HTTP sessions/gateway/Host/Origin/CSRF, dynamic pause, fair polling, and closed startup without root admission. A fresh actual-production-client→actualCRM-handler→reviewedSQL fixture covers office approval, exact invoice/replay/renewal, payment/refund/credit/final cancellation, preserved paid proof and held collection. That SQL fixture uses disclosed synthetic Auth/financial observations; it is not native admission or a genuine Stripe event.

Final native module/descriptor, physical admission/source manifest, isolated acceptance host/account/database bindings, real Stripe events/controlled confirmations and paired recovery are still being coordinated with the CRM chat. A separate explicitly bound acceptance artifact must isolate contract/account/mode, origin/portal, cookies/assets/API, storage and provider data; no sandbox fact may be relabeled as production money. Installation, integration review and final activation follow the owner's approval only after those checks pass. No new hosting subscription is required.
