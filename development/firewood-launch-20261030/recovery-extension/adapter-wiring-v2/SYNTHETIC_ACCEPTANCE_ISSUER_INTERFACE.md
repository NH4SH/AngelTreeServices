# Separate actual synthetic acceptance issuer — interface outline only

This document proposes the next separately reviewed implementation. It does not install a class, sign a receipt, register a source, create a key or remove any unbound Website barrier. The existing supervised QA collector stays restricted to its exact full200/201 QA profile. It must reject the new175/176 acceptance baseline and the separately named acceptance tables/database.

## Independent evidence issuer

Use a separate Root-owned development controller and signing identity that the CRM, Website and worker containers cannot read or invoke to manufacture an observation. Its input boundary is a detached independently pinned source registration; its observations come directly from the target/container/filesystem and independently read recovery bytes, not from producer-supplied digests or a readiness JSON file. Its output directory/socket is separate from `/admission` and `/release-admission`. The Website sees only root-owned immutable public acceptance control, public key and signed evidence, on verified read-only mounts.

The future controller needs these operations, with distinct input/output types:

- **Register actual synthetic source**: compare fresh target database name/OID/SID/marker/purpose, host/database boot, exact original175/176 plus separately reviewed25 acceptance names, owner/ACL/guard/schema postimages, exact actual nine containers/images/config/network/mounts, private per-role and HMAC custody/version digests, final adapter/client/DOC source closure, native topology and a new synthetic namespace/generation greater than3. Hash raw registration bytes. Preserve existing registration/history; do not reuse any HOME key, namespace, source record, descriptor, mount or receipt.
- **Observe closed source**: emit immutable development observation evidence only, including actual catalog/disk/role/session/producer flags and physical identity. This phase has `admitted:false`, cannot produce a Website proof, and makes no cloud/readback/restore claim.
- **Verify actual paired recovery**: take one explicitly paired DB/WAL/object/private-config/runtime capture for that registered source, independently read every required byte, restore it in a separate cold target, compare exact named inventory/catalog/data/file/version/guard identities and prove denied sessions and held producer state. Keep actual results as typed evidence with capture start in both clocks and exact manifest/file/component hashes. A local isolated recovery test must say `storageScope=isolated-development-local`; it must never set a cloud-provider/readback/retention proof flag. Cloud verification is a separate evidence type and remains absent until actually performed.
- **Issue synthetic lease**: only after the required actual evidence passes, atomically serialize one enabled **synthetic** writer for the exact accepted registration and issue a short signed acceptance-only lease. Use a different signed kind/domain and verifier from production, with mandatory synthetic purpose/database/OID/marker, registration digest, boot, namespace/generation, exact component/schema/overlay/DOC/private version digests, capture identities, evidence class and explicit mode booleans. An observation-only record cannot be upgraded by toggling a field. Signing must be unavailable on incomplete evidence.
- **Revoke/fence**: expired/missing/changed evidence, unsafe clock, capture age, lost independent timer/watch, target boot/identity change, paused/revoked modes or a newly appearing fence closes native SQL leases and exact role sessions/services. Hold restored flags by default. Keep one writer and retain prior evidence/history. Never stretch the deadline or sign a replacement capture time.

A proposed signature/domain string is a design choice for the future implementation, not a value registered by this work. Its production consumer must reject it, and its acceptance consumer must reject every HOME production receipt, namespace, key and database. The existing production `validateNativeWalReceipt` remains unchanged. No normalizer may relabel the projected QA ledger or local-storage evidence as production/cloud evidence.

## Website callback contract

The future separately hashed `native-proof-acceptance.mjs` should export the requested `createAdmissionVerifier` signature. Constructor validation must use fixed registered acceptance literals for database, schema, role/profile, descriptor origin/source/environment/account and test mode, plus immutable module/import/source/control pins. The literal database is the actual isolated acceptance database, never `postgres`; roles and final profile names remain unassigned until Root creates and reviews them. Missing actual fields fail rather than falling back to environment values.

Each returned async verifier is called with the **actual transaction** supplied by Website, once at BEGIN and again immediately before COMMIT for every requested mode. On each call:

1. Read and verify fresh root-owned public acceptance metadata, signed acceptance evidence, exact raw registered binding, authority fingerprint, boot, both clocks, independent fence and mode state. A constructor-cached success is insufficient.
2. Through that same transaction, read `current_database()`, database OID, `current_user` **and SESSION_USER**, current schema, SID, immutable purpose marker/comment and admission-binding identity. Read the actual native lease/topology/epoch/holder/capture/database-boot and root-controlled acceptance modes from the separately installed native helper. Do not use an operator session plus SET ROLE as a permitted app session.
3. Compare all physical/native/source identities against the independently verified signed registration and fresh opaque schema/owner/guard/component evidence. Hashes copied from the descriptor or query result cannot approve themselves. Ensure status and the requested mode are both admitted, and retain the separate native/application/provider mode gates.
4. Re-read the public master evidence after the SQL query. Require unchanged registration/key/namespace/generation/boot/sequence/modes and no new fence. Compute `backupAgeMs` as an integer from actual monotonic capture start, require0 <= age <280000 and enforce the wall-clock age independently. Set `expiresAtMs` to the integer minimum of the actual native SQL lease, signed master expiry, remaining monotonic280-second deadline and `now+14000`; require it strictly after now.
5. Only then return the Website contract: `admitted:true`, exact `systemIdentifier`, `releaseSha256`, `schemaSha256`, `recoveryBindingSha256`, `authorityPublicKeyFingerprint`, integer `backupAgeMs` and `expiresAtMs`. Additional target identity stays authenticated inside the adapter. A failed end-of-transaction check throws and rolls back all business changes.

The Website wrapper already checks these five hash/SID fields and both numeric bounds at both transaction boundaries. The issuer/native adapter supplies the missing provenance and live SQL enforcement; a test fixture returning the right object shape does not satisfy it. The requested five mode verifiers must also remain independent: pausing collection/sending must not create authority for another operation, and allowing status cannot imply collection or provider dispatch.

## Required actual fault tests before enabling the callback

Use real native request/worker SESSION_USER connections in the isolated target and independently controlled actual evidence. Prove rollback when the lease expires between BEGIN and COMMIT; a fence appears; status or a requested mode is revoked; boot/SID/OID/marker/topology/namespace/generation changes; the source/DOC/private bytes or key version changes; a same-count table replacement occurs; an old signed receipt/registration is replayed; or signed pairing identities disagree with the actually restored bytes. Keep healthNOLOGIN. Confirm role denial without operator bypass and no active receipt/source/worker gate restored from a backup.

Only actual separately scoped sandbox/provider bindings may test collection, refunds, cancellations or restricted test sending. Recovery evidence alone never grants those effects. The issuer must continue to report cloud verification absent until Root actually performs it. The current baseline and closed source class cannot issue any such proof.
