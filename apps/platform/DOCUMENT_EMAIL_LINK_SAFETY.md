## Findings and changes

The previous delivery guard accepted an active token ID without fully binding it to the selected document and its current customer/organization. A rollback-only reproduction against migration 115 admitted another document's token for the same customer. It also admitted a token that expired after the transaction began, because expiry used the transaction's start time. Both reproductions now fail safely.

Migration `20261022194856_bind_document_email_capabilities.sql` adds a private invoker helper and narrowly replaces the old token-check loop in the existing source predicate. Quote, invoice and change-order tokens must belong to the exact selected source and its current customer/organization. Change-order approval contacts must also match. Revocation and expiry are checked at admission using the current wall clock, including after lock waits. An exact preimage check preserves the accumulated authorization, source, recipient, sender-block, notification and appointment rules. There are no new public RPCs, client grants, RLS changes or financial transaction changes.

Quote follow-up, invoice payment reminder and overdue reminder preparation now freezes the verified token ID alongside the existing immutable delivery payload. The guard requires one matching document-family token for these actionable reminders. It checks the same identity at dispatch/retry rather than substituting a newly generated URL. Older unattempted frozen reminders without that identity are held through the existing source-changed review path; they are not rebuilt or automatically resent. Accepted/uncertain delivery history is retained, and history-only reconciliation does not resend after a link is revoked.

A shared server-only reader verifies source ownership, revocation, expiry and the recovered/supplied raw token's hash before constructing quote/invoice links. Existing create/reuse RPCs retain their authority and retry semantics. Reminder preparation does not generate or rotate links. Submitted office-email URLs are reconstructed on the configured CRM origin after validation, preventing an arbitrary submitted host from being forwarded to the customer.

Existing individual and combined proposal emailing, CC, per-proposal decisions, non-expiring historical links, explicit link replacement/revocation, delivery review and provider idempotency remain. No new combined-email selection limit is introduced: a 26-proposal case passes, while the existing context byte bound and separate 25-proposal legacy-replacement limit remain unchanged. Employee, dashboard and prior application work are preserved. No frontend component or style changes are included.
